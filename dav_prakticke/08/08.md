## Indexes and query plans

`EXPLAIN SELECT ...` zobrazí (bez výpočtu dotazu) plán vyjadrený pomocou fyzických operátorov. `EXPLAIN ANALYZE SELECT ...` dotaz aj vypočíta, ale namiesto výsledných riadkov vypíše plán so skutočnými časmi. Sledujte najmä spôsob prístupu k tabuľkám, algoritmus pre výpočet joinu a `Execution Time`. Hodnoty `cost` sú odhady v abstraktných jednotkách, nie namerané milisekundy.

V úlohách E1--E5 pozorujte, čo sa zmenilo po pridaní indexu alebo po zmene veľkosti tabuliek. Prvé spustenie môže načítať dáta do cache a ďalšie tak môžu byť rýchlejšie. Každý variant dotazu preto spustite niekoľkokrát a porovnávajte medzi sebou časy opakovaných behov, oddelene od prvého spustenia. Konkrétny plán a časy závisia od počítača, nastavení a verzie PostgreSQL; nemusíte dostať rovnaký plán ako spolužiaci.

### E1: WHERE a index

Na serveri `cvika` použite svoju existujúcu databázu ([prístup k PostgreSQL](../../technical_info/sql.md#postgresql)). Pri lokálnej inštalácii môžete použiť osobitnú databázu, napr. vytvorenú príkazom `createdb cvicenie8`; vtedy k nižšie uvedeným príkazom `psql` doplňte `-d cvicenie8`. V adresári cvičenia načítajte [explain_setup.sql](explain_setup.sql):

```sh
psql -v ON_ERROR_STOP=1 -f explain_setup.sql
psql
```

Skript vytvorí známu schému `department`, `employee`, `project`, `emp_projects`, zatiaľ iba s primárnymi kľúčmi. Naplní 1 000 oddelení a 1 000 000 zamestnancov; projekty zatiaľ ostanú prázdne. Veľa riadkov možno vložiť jedným príkazom pomocou `generate_series`. Napríklad údaje o zamestnancoch sa generujú takto (skript ich už vložil, nevkladajte ich druhýkrát):

```sql
INSERT INTO employee (emp_id, name, job, salary, superior, dept_id)
SELECT i, 'Employee ' || i, 'analyst',
       1000 + floor(random() * 10000), NULL,
       1 + floor(random() * 1000)::integer
FROM generate_series(1, 1000000) AS g(i);
```

`generate_series(1, 1000000)` dodá milión hodnôt `i`. `random()` vracia číslo z intervalu `[0, 1)`; posledný výraz tak vyberie oddelenie od 1 do 1 000. Skript po naplnení spustí `VACUUM ANALYZE`, ktorý pripraví tabuľky a štatistiky pre nasledujúce experimenty.

Spustite oba dotazy:

```sql
EXPLAIN ANALYZE
SELECT * FROM employee WHERE salary BETWEEN 4000 AND 4010;

EXPLAIN ANALYZE
SELECT * FROM employee WHERE salary < 6000;
```

Pridajte index a zopakujte tie isté dva dotazy:

```sql
CREATE INDEX i_emp_salary ON employee (salary);
```

Použil PostgreSQL index v oboch prípadoch? Pri ktorom dotaze ste pozorovali výrazné zrýchlenie? Nakoniec index zrušte:

```sql
DROP INDEX i_emp_salary;
```

### E2: ORDER BY a údaje uložené v indexe

Pokračujte s rovnakými dátami, bez indexu `i_emp_salary`. V `psql` zapnite `\timing on`, aby ste videli aj čas vytvorenia indexu:

```sql
EXPLAIN ANALYZE
SELECT emp_id, name, salary
FROM employee
ORDER BY salary DESC, emp_id
LIMIT 20;
```

Najprv pridajte index s kľúčmi `salary DESC, emp_id ASC`, bez `INCLUDE`, a dotaz zopakujte. Ostal v pláne samostatný `Sort`? Aký operátor pristupuje k tabuľke `employee`?

Potom tento index zrušte a vytvorte index s rovnakými kľúčmi, ktorý navyše pomocou `INCLUDE` uloží aj `name`. Syntax pre zahrnutie ďalších stĺpcov nájdete v [dokumentácii](https://www.postgresql.org/docs/current/indexes-index-only-scans.html). Dotaz opäť zopakujte. Objavil sa `Index Only Scan`?

Poznámka: Pri súbežných zmenách dát musí databáza rozhodnúť aj to, ktoré zmeny má konkrétny dotaz vidieť. Informácie potrebné na toto rozhodnutie nie sú priamo v indexe, preto môže aj `Index Only Scan` niekedy pristúpiť k riadku v tabuľke. Ak už má databáza zaznamenané, že ďalšia kontrola nie je potrebná, tento prístup vynechá; takéto pomocné informácie pripravuje aj `VACUUM`. (Keď do hry vstúpia transakcie viacerých používateľov súčasne, všetko sa ešte viac skomplikuje, akoby to nebolo beztak dosť zložité. To je jeden z dôvodov, prečo tvorcovia DBMS pristupujú k pridávaniu novej funkcionality veľmi opatrne.)

Porovnajte čas dotazu vo všetkých troch prípadoch a všimnite si aj čas vytvorenia indexov. Nakoniec pridaný index zrušte.

### E3: Index môže urýchliť join

Stále použite údaje z E1:

```sql
EXPLAIN ANALYZE
SELECT d.name, e.name
FROM department d
JOIN employee e ON e.dept_id = d.dept_id
WHERE d.dept_id BETWEEN 1 AND 3;
```

Navrhnite a vytvorte jeden index na `employee`, ktorý pomôže pri tomto dotaze. Zopakujte dotaz a porovnajte čas, algoritmus joinu a prístup k tabuľke `employee`.

Pomohlo by pridať aj index na `department(dept_id)`? Pozrite si pomocou `\d department`, ktoré indexy už na tabuľke existujú.

### E4: Rovnaký dotaz, rôzne veľkosti tabuliek

Použite tento dotaz v štyroch nižšie uvedených stavoch databázy:

```sql
EXPLAIN ANALYZE
SELECT d.name, e.name
FROM department d
JOIN employee e ON e.dept_id = d.dept_id;
```

| Stav | Zamestnanci | Oddelenia |
|---|---:|---:|
| malá/malá | 100 | 100 |
| veľká/malá | 1 000 000 | 100 |
| malá/veľká | 100 | 1 000 000 |
| veľká/veľká | 1 000 000 | 1 000 000 |

Údaje môžete generovať úpravou príkazov zo skriptu E1. Jednoduchšie je využiť jeho parametre. Nasledujúce príkazy spúšťajte v termináli po jednom: po každom načítaní prejdite do `psql` a pozrite plán dotazu, až potom načítajte ďalší stav.

```sh
psql -v ON_ERROR_STOP=1 -v n_employees=100 -v n_departments=100 -f explain_setup.sql
psql -v ON_ERROR_STOP=1 -v n_employees=1000000 -v n_departments=100 -f explain_setup.sql
psql -v ON_ERROR_STOP=1 -v n_employees=100 -v n_departments=1000000 -f explain_setup.sql
psql -v ON_ERROR_STOP=1 -v n_employees=1000000 -v n_departments=1000000 -f explain_setup.sql
```

Skript vždy vytvorí tabuľky nanovo vrátane štatistík a odstráni aj indexy z predchádzajúcich úloh; ostanú iba indexy primárnych kľúčov. Názvy `n_employees` a `n_departments` sú parametre skriptu; čísla určujú počty generovaných riadkov.

Všimnite si, či sa mení algoritmus joinu a spôsob prístupu k tabuľkám, hoci SQL dotaz ostáva rovnaký. Aké rozdiely ste pozorovali medzi oboma asymetrickými stavmi?

### E5: Väčší plán a NOT EXISTS

V termináli obnovte základné údaje z E1 a vytvorte index na `employee(dept_id)`:

```sh
psql -v ON_ERROR_STOP=1 -f explain_setup.sql -c 'CREATE INDEX i_emp_dept ON employee (dept_id);'
```

V `psql` pripravte projekty a každému druhému zamestnancovi priraďte jeden z nich:

```sql
INSERT INTO project (proj_id, name)
SELECT i, 'Project ' || i FROM generate_series(1, 1000) AS g(i);

INSERT INTO emp_projects (emp_id, proj_id)
SELECT 2 * i, 1 + (i % 1000)
FROM generate_series(1, 500000) AS g(i);

ANALYZE emp_projects;
```

Pozrite si plán dotazu počítajúceho zamestnancov bez projektu na vybraných oddeleniach:

```sql
EXPLAIN ANALYZE
SELECT d.dept_id, count(*)
FROM department d
JOIN employee e ON e.dept_id = d.dept_id
WHERE d.dept_id BETWEEN 1 AND 3
  AND NOT EXISTS (
      SELECT 1
      FROM emp_projects ep
      WHERE ep.emp_id = e.emp_id
  )
GROUP BY d.dept_id;
```

Nájdite časť plánu zodpovedajúcu `NOT EXISTS`. Pridajte index na `emp_projects`, ktorý môže urýchliť vyhľadávanie pre jednotlivých zamestnancov, a dotaz zopakujte. Porovnajte čas a zistite, ktorá časť plánu sa zmenila. Znamená výskyt operátora `Hash` v pláne použitie hash indexu?
